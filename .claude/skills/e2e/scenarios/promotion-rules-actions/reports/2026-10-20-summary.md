## What is proven, on both providers

- A promotion validation and its deployment use the rules of the target of the promotion: the uat
  branch file value, the uat-only rule, the issue value of preprod, the exclusion of main, and the
  `PRA_SECRET_<BRANCH>` of the target. The org holds the expected value of every rule after each of
  the six deployment jobs, quick deployed or not.
- The rule added by S2 in `config/.sfdx-hardis.yml` applies in its own validation and travels with
  the promotions; the value S3 changed stays in integration (the promotion branches never hold it).
- The actions of S1 run once in each org branch (pre command in each validation, post command, Apex
  script and manual step in each deployment), with their statuses in uat and main.
- Order inside `deploy:smart`: the pre-deployment command sees the files of git; the main-only removal
  takes the Apex class out of `package.xml` before the rules list their files, so `pra-apex-host`
  has nothing to change and the org keeps the preprod host; the post-deployment command sees the
  files of git again (restored); the Apex action reads the replaced label value in the org.
- No secret value in any job log or Pull Request comment.
- The Pull Request modal and the DevOps Pipeline of the extension show what the provider holds.

## What the runs found

No defect of sfdx-hardis. Defects of the scenario itself, fixed before the runs above:

- On Windows, git checked the test clone out with CRLF and the S2 edit (looking for LF) did nothing:
  S2 was merged without its label (run 1). The clone now uses `core.autocrlf false`, and every story
  edit is checked before its commit.
- The org step tested `connectedStatus`, which a scratch org does not report (run 2): it logged out
  the orgs of run 1 and then hit the Dev Hub limit.
- Promotion validation logs were named `UAT-check` and read as `uat-check`, which only works on a
  file system that ignores case.

## What these runs did not cover

- Azure DevOps and Bitbucket Cloud: the scenario runs on GitHub and GitLab only.
- One org for the four branches: the values are checked right after each deployment, not side by
  side in four orgs.
- The VS Code panels are checked through the calls they make (`check-pr-modal.cjs`,
  `check-pipeline.cjs`), not rendered.
- The built-in rules (Flow end elements, unknown user permissions) and the `text` rule across several
  files are not in this project: the replacement-rules scenario covers them on one branch.
