# Update the built-in replacement rules for a new Salesforce release

Built-in replacement rules remove, before a deployment, what the target org would refuse because of
its API version: XML elements it does not know yet (a sandbox on the preview release deploying to
production) or no longer accepts, and user permissions it does not have. Each Salesforce release
(three per year, API version + 1) can add some. This skill finds them, updates the code and
regenerates the documentation page.

## Files

| File                                                                   | Role                                                                                                                                                                                                                                                 |
|------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `src/common/replacementRules/builtIn/builtInReplacementRules.ts`       | `BUILT_IN_REPLACEMENT_RULES`: one entry per rule (id, files, xmlPaths, `introducedIn` or `removedIn`, `defaultEnabled`, source). Hand written.                                                                                                       |
| `src/common/replacementRules/builtIn/userPermissionsByApiVersion.ts`   | User permissions by the API version that introduced or removed them. Generated by `scripts/refresh-user-permissions.mjs`, never edited by hand.                                                                                                      |
| `src/common/replacementRules/builtIn/builtInRulesDoc.ts`               | Builds the markdown of the documentation page from the two files above.                                                                                                                                                                              |
| `scripts/build-builtin-replacement-rules-doc.ts` (repo root)           | Writes the page: `node --import tsx scripts/build-builtin-replacement-rules-doc.ts`.                                                                                                                                                                 |
| `docs/salesforce-devops-config-replacement-rules-builtin.md`           | The generated page. `test/common/replacementRules/builtInRulesDoc.test.ts` fails when it is not up to date or misses a rule.                                                                                                                         |
| `docs/salesforce-devops-config-replacement-rules.md`                   | Overview page: its "Built-in rules" section shows examples only, update it when an example rule changes.                                                                                                                                             |
| `src/common/replacementRules/builtInRemovalRule.ts` and its subclasses | Class of the built-in rules (removes the `xmlPaths` elements). A subclass (`flowEndsBuiltInRule.ts`, `unknownUserPermissionsBuiltInRule.ts`) handles a removal that needs more than deleting the element; `index.ts` maps the `handler` field to it. |

Scripts of this skill (run them from the repository root, they import `@salesforce/core` from its
`node_modules`):

| Script                                   | Use                                                                                                                                                |
|------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------|
| `scripts/describe-metadata-elements.mjs` | Compares the element tree of metadata types (Metadata API `describeValueType`) between two API versions and prints the added and removed elements. |
| `scripts/refresh-user-permissions.mjs`   | Describes `PermissionSet` at every API version on one or more orgs and rewrites `userPermissionsByApiVersion.ts`. `--dry-run` only prints.         |

## Prerequisites

- An org that already answers at the new API version N: a sandbox on the preview release (pre-release
  sandboxes upgrade about a month before production), or any org once the release is out. Check:
  `sf api request rest services/data/` lists `"version":"N.0"`.
- For user permissions, two orgs with different licenses give a better list: the Dev Hub (Developer
  Edition) and an Enterprise Edition sandbox. Each org only shows the permissions of its licenses and
  features, so a permission no described org has is never listed. That is fine: with a connection, the
  rule reads the target org itself; this list only serves `preview` without `--target-org`.
- Run `sf` commands with orgs the user authorized; ask for the aliases if `DevHub` is not enough.

## Steps

### 1. Find the new elements

```sh
node .claude/skills/replacement-rules-builtin-update/scripts/describe-metadata-elements.mjs --org <alias at N> --from <N-1> --to <N>
```

Default types: Flow, Profile, PermissionSet, PermissionSetGroup, CustomObject, CustomField, Layout,
FlexiPage, CustomApplication, a few Settings, ExperienceBundle, Bot, GenAiPlannerBundle. Add
`--types A,B` for others (any Metadata API type name), `--out <dir>` to keep the full trees. Lines with
`+` are new at N (`introducedIn: N`), lines with `-` are gone at N (`removedIn: N`). A new complex
element prints once, without its children.

Then read the release notes and the Metadata API Developer Guide of the release: search for
"Available in API version N.0 and later" and "Removed in API version N.0", and the "New and Changed
Metadata Types and Fields" page of the release notes. They explain what each element does, which the
describe cannot tell.

### 2. Decide which elements become rules

Not every new element deserves a rule. Add one when all of these hold:

- A normal retrieve from an org on the new release writes it into files people commit (Flow Builder,
  Profiles and Permission Sets retrieved whole, Settings). An element only set by a new feature that
  production will not have either is not worth it.
- An org one release behind refuses the deployment because of it (`invalid at this location`).
- It is a leaf or a block that can be deleted alone, and the file stays valid without it. If other
  elements point to it (connectors to a Flow element, like `<ends>`), it needs a handler: see
  `flowEndsBuiltInRule.ts`: add a subclass of `BuiltInRemovalRule` overriding `removeElements` (and
  `prepare` when it must read the target org), a value of the `handler` field in `utils/types.ts`, and
  its case in `createReplacementRule` (`index.ts`).

Then choose `defaultEnabled`:

- `true` when removing it changes nothing the user sees at run time on the older org: visual settings,
  metadata of features the older org does not have, a default value written explicitly.
- `false` when removing it changes what the component does (a Get Records `limit`, a trigger, a filter).
  The engine then only warns that the deployment will fail and names the rule.

For a removed element (`-` line), `removedIn: N`: deploying it to an org at N or above fails, so the
rule deletes it there.

### 3. Edit `builtInReplacementRules.ts`

Add each rule to the group it belongs to (Flows, Profiles and permission sets, Settings no longer
accepted), newest version first inside a group, following the existing entries:

- `id`: `builtin-<metadata>-<element>` in kebab case, unique, never renamed once released (users
  turn rules on or off by id in their config and issue).
- `description`: what is removed and why it is safe, one line, plain words.
- `files`: glob of the metadata files (reuse `FLOWS`, `PROFILES_AND_PERMISSION_SETS`).
- `xmlPaths`: replacement rules path syntax (see the header of `utils/xmlPath.ts`): `Flow/screens/styleSettings`,
  `//dayOfMonthToRun`, `Flow/*/group`, `Profile/objectPermissions/viewAllFields[.=false]`.
- `introducedIn: N` or `removedIn: N`.
- `source`: `` `${MDAPI} vN (Type)` `` or the release notes page.

Update the header comment of the file when the range of guides changes ("v60 to v68").

### 4. Refresh the user permissions

```sh
node .claude/skills/replacement-rules-builtin-update/scripts/refresh-user-permissions.mjs --org DevHub --org <enterprise sandbox> --to <N> --dry-run
node .claude/skills/replacement-rules-builtin-update/scripts/refresh-user-permissions.mjs --org DevHub --org <enterprise sandbox> --to <N>
```

It describes `PermissionSet` at every version from 50 to N (about a minute per org), keeps the
entries already in the file, adds the new ones and updates the "API 50 to N" range of the header. Read
the output before keeping the result:

- `new X: introducedIn N`: expected, a few dozen per release.
- `moved X`: the describes place a known permission at another version. Usually a better answer
  (another org), check one or two.
- `REMOVED X: removedIn N`: a permission no described org shows anymore at N. Salesforce rarely
  removes one: it is often a feature switched off in that org, or a license that expired. Keep it only
  if the release notes or the guide confirm the removal; otherwise revert that entry.
- `WARNING ... gap`: a permission that disappears and comes back across versions, a feature switched on
  and off. Check it before keeping it.

`--min-intro 58` (default) skips permissions older than any org still running. A run on the same data
writes the file unchanged.

### 5. Tests

- Add one engine test per rule that needs a handler or an unusual path, in
  `test/common/replacementRules/ruleEngine.test.ts` (look at the `builtin-flow-ends` and
  `builtin-unknown-user-permissions` tests). A plain element removal is covered by the generic tests.
- `ruleConfig.test.ts` checks every id starts with `builtin-` and is unique.

### 6. Regenerate the documentation page

```sh
node --import tsx scripts/build-builtin-replacement-rules-doc.ts
```

Never edit `docs/salesforce-devops-config-replacement-rules-builtin.md` by hand. If a rule shown as an
example in `docs/salesforce-devops-config-replacement-rules.md` changed, update that page too.

### 7. Check

```sh
yarn compile
yarn lint
npx mocha test/common/replacementRules/*.test.ts
```

cspell skips `userPermissionsByApiVersion.ts` (listed in `.github/linters/.cspell.json`) and the
permission list of the page (cspell markers written by the generator). A new rule description or id can
still hold an unknown word: add it to the cspell `words` list only if it is a real Salesforce term.

### 8. Deliver

- One `CHANGELOG.md` line under `## [beta] (main)`, for example: "Replacement rules (Beta): built-in
  rules for the API 69.0 Flow and Permission Set elements". No list of elements (the page has it).
- VS Code extension: no change needed, its Built-in rules tab reads `sf hardis:project:replacement:list --json`.
  If the screenshot `docs/assets/images/replacement-rules-builtin.png` matters for the release, refresh
  it from the extension (`yarn screenshots replacement-rules-tabs` there, then `scripts/build-doc-images.py`).
- Training impact: none, the labs do not list built-in rules.
- When a rule has a handler, or the release changes how the deployment API version behaves, run the
  `replacement-rules-e2e` skill (its sample project takes `API=<N-1>` to deploy below the new release).

## Traps

- `describeValueType` is not wrapped by jsforce v2: the script calls the SOAP operation with
  `conn.metadata._invoke('describeValueType', { type })`.
- The connection version decides the answer: `org.getConnection('N.0')`. An org not yet on the release
  fails at N: use a preview sandbox.
- A Developer Edition org lacks most industry clouds: its element trees and permissions are a lower
  bound. An element missing from the diff can still be new; the release notes have the last word.
- Sort user permission names by code point (`sort()`), like the generator: `localeCompare` reorders
  names like `PRMChannelMgmtConsoleUser` and makes a diff of nothing.
- The deployment API version is the lowest of the org, `sourceApiVersion` and the package.xml version
  (`resolveDeployApiVersion` in `engine/ruleEngine.ts`): a project still on an old `sourceApiVersion` triggers
  `introducedIn` rules even against an org on the newest release. That is expected.
